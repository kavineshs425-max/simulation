# my_boat Propulsion System — v1 (bow pair + steerable stern drive)

> A second arrangement now exists: **v2**, two centreline laterals straddling
> the CG plus a fixed axial stern propeller — see
> [THRUSTERS_V2.md](THRUSTERS_V2.md). It is a separate set of files
> (`*_v2.xacro`, `thrusters_v2.yaml`, `my_boat_world_v2.launch.py`); everything
> described below is unchanged and still spawnable.

Functional propulsion subsystem for the custom USV `my_boat` in VRX / Gazebo
Harmonic. Three thrusters reproduce the real vessel: two fixed bow tunnel
thrusters and one steerable stern drive. Thrust is generated by Gazebo's
force-based marine plugins (NOT by the mesh geometry), so commands produce
realistic forces and moments and the model is ready for a ROS 2 force allocator
and dynamic-positioning controller.

---

## 1. Hardware → simulation mapping

| Unit | Real hardware              | Role                         | Max thrust | DOF produced            |
|------|----------------------------|------------------------------|-----------:|-------------------------|
| T1   | APISQUEEN U92 Pro          | Port bow tunnel, fixed       | ± 98 N     | sway (+Y) & yaw         |
| T2   | APISQUEEN U92 Pro          | Stbd bow tunnel, fixed       | ± 98 N     | sway (+Y) & yaw         |
| T3   | Torqeedo Cruise 3.0 R      | Stern drive, steerable       | ± 632 N    | surge (+X), vectored yaw|
| —    | ServoCity HD linear servo  | Steering of the T3 leg       | ± 21°      | rotates the T3 vector   |

All three thrusters are **reversible** (commands saturate symmetrically at
`±max_thrust_cmd`). Steering is a position-controlled revolute joint limited to
**±21° (±0.3665 rad)**.

## 3. Link & joint hierarchy

Produced by the macros in `urdf/thrusters/my_boat_engine.xacro`
(verified with `check_urdf`):

```
my_boat/base_link
├── T1_propeller_link           (continuous T1_propeller_joint, yaw −90°, axis x ⇒ −Y)
├── T2_propeller_link           (continuous T2_propeller_joint, yaw +90°, axis x ⇒ +Y)
└── T3_steering_mount_link      (fixed mount at the pivot, yaw 180° ⇒ faces −X)
    └── T3_shaft_link           (revolute  T3_steering_joint, axis z, ±21°)
        └── T3_propeller_link   (continuous T3_propeller_rotation_joint, axis −x ⇒ +X)
```

The bow thrusters (T1/T2) are **bare propellers attached directly to base_link**
— no housing and no shaft, as only the steerable Torqeedo (T3) has a shaft. T3
still matches the required architecture: `base_link → steering_mount_link →
steering_joint(z) → shaft_link → propeller_rotation_joint → propeller_link`.

The only mesh used is the **reused WAM-V `propeller.dae`**, on the three
propeller links (the parts that spin / act as a joint). The steerable T3 leg is
a simple **cylinder**; all collisions are primitives (cylinders/boxes). Per the
spec, geometry is visual/collision only —
**thrust is plugin-generated**, never from mesh geometry.

## 4. Joint configuration

### Steering joint `T3_steering_joint` (revolute, z)
Models the ServoCity HD linear servo (33 lb ≈ 147 N, ~1.7 s sweep) acting
through a ~0.15 m tiller arm.

| Property   | Value      | Rationale                                          |
|------------|------------|----------------------------------------------------|
| lower/upper| ∓0.3665 rad| ±21° steering range from the drawing               |
| effort     | 30 N·m     | 147 N × 0.15 m ≈ 22 N·m demand, with margin        |
| velocity   | 0.45 rad/s | 0.733 rad sweep in ≈1.7 s                           |
| damping    | 8.0        | lead-screw actuator is heavily damped, ~non-backdrivable |
| friction   | 3.0        | static resistance of the screw drive               |

### Propeller rotation joints (continuous, x) — visual only
`T1_propeller_joint`, `T2_propeller_joint`, `T3_propeller_rotation_joint`.
Spun by the Thruster plugin at a speed proportional to thrust magnitude (sign =
thrust sign ⇒ reverse spin for reverse thrust). `damping=0.01`, `friction=0.0`.
**No physical force comes from these joints** — they exist for visualisation and
to give the Thruster plugin a propeller to drive.

## 5. Thruster physics (force plugins)

Configured in `urdf/thrusters/my_boat_thruster_config.xacro`. Each unit uses
`gz::sim::systems::Thruster` with `velocity_control=true`:

```
T = thrust_coefficient · ρ · |n| · n · D⁴      (ρ=1000, D=0.10 m, Ct=0.004422)
```

The command is **thrust in Newtons**; the plugin back-solves the propeller
angular velocity `n`, drives the spin joint, and applies the force along that
joint's axis at the propeller link. `max_thrust_cmd` / `min_thrust_cmd` cap the
force at the real hardware limits, so commanded Newtons are what get applied:

| Unit | joint driven                    | max_thrust_cmd | min_thrust_cmd | \|n\|max  |
|------|---------------------------------|---------------:|---------------:|----------:|
| T1   | T1_propeller_joint              | +98 N          | −98 N          | 14.9 rad/s|
| T2   | T2_propeller_joint              | +98 N          | −98 N          | 14.9 rad/s|
| T3   | T3_propeller_rotation_joint     | +632 N         | −632 N         | 37.8 rad/s|

Because the thrust is applied along the **propeller joint axis transformed into
the world**, steering the T3 leg vectors the surge force, and the +90° bow
mounts make T1/T2 push laterally — i.e. forces & moments are physically correct.

Steering uses `gz::sim::systems::JointPositionController`
(`use_velocity_commands=true`) so the leg slews to the commanded angle like a
real servo.

## 6. Command (topic) interfaces

Gazebo transport topics created by the plugins, bridged to ROS 2 by
`config/thrusters.yaml`:

| Quantity        | Topic                          | ROS type            | gz type       | Units |
|-----------------|--------------------------------|---------------------|---------------|-------|
| T1 thrust       | `/my_boat/thrusters/T1/thrust` | std_msgs/Float64    | gz.msgs.Double| N     |
| T2 thrust       | `/my_boat/thrusters/T2/thrust` | std_msgs/Float64    | gz.msgs.Double| N     |
| T3 thrust       | `/my_boat/thrusters/T3/thrust` | std_msgs/Float64    | gz.msgs.Double| N     |
| T3 steering pos | `/my_boat/thrusters/T3/pos`    | std_msgs/Float64    | gz.msgs.Double| rad   |

### Sign conventions (for the allocator) — per `VRX_Thruster_Configuration.docx`
* `T1 thrust > 0` → force toward **starboard (−Y)** at the port-bow station.
* `T2 thrust > 0` → force toward **port (+Y)** at the starboard-bow station.
* `T3 thrust > 0` → surge **forward (+X)**, rotated by the steering angle.
* `T3 pos > 0` → leg yaws about **+Z** (swings the stern-thrust vector to port).

### Allocation model (3-DOF: surge X, sway Y, yaw N)
With α = T3 steering angle and lever arms in metres:
```
X ≈  T3·cos(α)
Y ≈ −T1 + T2 + T3·sin(α)
N ≈  1.03·(T2 − T1) − 1.50·T3·sin(α)
```
Because T1 and T2 share the same longitudinal station (x = +1.03 m), the bow
pair's lateral force always couples sway and yaw (`N_bow = 1.03·Y_bow`); the
azimuthing stern unit T3 (lever −1.50 m) supplies the independent third axis, so
the 3×3 map is full-rank and invertible by the allocator. (Verified numerically:
+cmd thrust directions are T1→−Y, T2→+Y, T3→+X, and T3 at +21° vectors to port.)

## 7. Integration & run instructions (VRX / Gazebo Harmonic)

1. **Build & source** (from the workspace root):
   ```bash
   cd ~/kavinesh/gazebo_vfx/vrx_garden_ws
   colcon build --packages-select my_boat_description my_boat_gazebo
   source install/setup.bash
   ```

2. **Start a VRX world**, then **spawn the boat** (the spawn launch also starts
   the thruster bridge by default):
   ```bash
   ros2 launch vrx_gz competition.launch.py world:=sydney_regatta
   ros2 launch my_boat_gazebo spawn_my_boat.launch.py        # add bridge:=false to skip
   ```

3. **Drive the thrusters** from ROS 2:
   ```bash
   # Full-ahead stern drive (632 N)
   ros2 topic pub -1 /my_boat/thrusters/T3/thrust std_msgs/msg/Float64 "{data: 632.0}"
   # Steer the leg +21° (0.3665 rad)
   ros2 topic pub -1 /my_boat/thrusters/T3/pos    std_msgs/msg/Float64 "{data: 0.3665}"
   # Bow thrust: both to starboard (T1>0 → −Y, T2<0 → −Y) ⇒ sway + yaw
   ros2 topic pub -1 /my_boat/thrusters/T1/thrust std_msgs/msg/Float64 "{data:  98.0}"
   ros2 topic pub -1 /my_boat/thrusters/T2/thrust std_msgs/msg/Float64 "{data: -98.0}"
   ```
   Without the ROS bridge you can command Gazebo directly:
   ```bash
   gz topic -t /my_boat/thrusters/T3/thrust -m gz.msgs.Double -p 'data: 632.0'
   ```

### Quick validation checklist
* `check_urdf` shows the tree in §3 — **passes**.
* `gz sdf -p my_boat.urdf` converts with **no errors/warnings** — **passes**.
* T3 thrust > 0 with `pos=0` drives straight ahead; with `pos=0.3665` the boat
  turns — confirms thrust vectoring through the steering joint.
* T1=+98 alone pushes the bow to starboard (−Y) and yaws it — confirms the bow
  lateral thrust + lever (sway/yaw coupling).
